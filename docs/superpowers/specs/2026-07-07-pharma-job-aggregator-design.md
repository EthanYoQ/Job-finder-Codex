## 设计状态

本规格基于已完成的 Grill-me 需求收敛、PRD 文档和 Product Design 审核。用户已确认当前方向；2026-07-15 最新修订是：固定 60 家目录，P0 正式完成前至少 45 家达到稳定自动更新，每天北京时间 00:01 更新一次。本规格不包含代码实现。

当前状态不是 P0 可正式上线状态。目录固定为 30 家外资药企和 30 家国内药企，不使用候选池替换名单；正式完成前必须至少有 45 家公司达到稳定自动更新。

人福医药与华北制药保留在固定 60 家目录中，但属于用户授权的一期排除项，不对其职位完整性作声明。首次上线前低于 45 家时只能进行受限内部预览；规则和公司配置冻结后只运行两轮正式资格抓取，第二轮仍不足 45 家即暂停并通知用户。首次上线完成后改为逐公司独立日更，不因当前总数低于 45 而清空其他成功公司。`job.orz.md`、人工智能分类和辅助翻译不属于本期上线条件。

## 产品定位

产品是国内医药行业官方招聘信息聚合网页应用。它只解决职位发现和跳转，不做站内投递、简历管理、申请进度管理、求职者账号或招聘方工具。

首页不是营销页，而是城市必选的职位发现工作台。用户进入后先同意隐私政策和服务条款，再选择城市；职位类别、关键词、公司筛选和排序是辅助筛选。核心路径是：

1. 选择城市。
2. 可选职位类别、关键词、公司筛选。
3. 查看按公司聚合的职位结果。
4. 展开公司查看极简岗位列表。
5. 点击官方链接跳转到公司官方招聘来源。

## P0 成功标准

- 目录固定覆盖 30 家外资药企和 30 家国内药企，无替换。
- 至少 45 家公司达到稳定自动更新。
- 首次上线时，稳定自动更新公司数达到至少 45 家并通过门禁后才可对外开放；首次上线前不足 45 家时，已验证子集和全部官方入口只能用于受限的内部候选预览。上线后按公司独立更新，不设置运行期全站最低数。
- 所有已验证公司必须能从官方主页或官方招聘页追溯到招聘入口。
- P0 前台只展示社会招聘岗位。
- 校园招聘只记录入口状态，不进入搜索结果。
- 首页在手机端可完整完成城市搜索、筛选、公司展开和官方跳转。
- 数据每天北京时间 00:01 自动抓取一次，并支持后台手动单公司重抓。
- 最近一次合格更新达到 30 小时时停止公开相应职位；明确抓取失败时立即停止公开该公司的职位，但保留数据库记录以便修复。
- 前台只显示全站最后一次抓取时间。
- 无公开 API、无批量导出、无深分页暴露。

首次上线资格验证与生产调度分离：验证期间不启动永久调度进程，只对隔离的候选数据库连续执行两次完整强制抓取；第二轮后立即计算 45 家门槛。通过首次上线门禁后，才启用每天 00:01 持续运行的生产调度器。

“已验证可抓取”的判定标准：

1. 公司官方主页或官方招聘页能追溯到社招入口。
2. 抓取器能从该入口返回结构化岗位记录。
3. 至少连续两次成功抓取返回稳定字段。
4. 字段至少包含公司、岗位标题、官方来源链接、城市或地点信息。
5. 若来源只提供列表页链接，也必须能把官方入口和岗位标题保存为可审计证据。

Implementation note: `npm run p0:launch-readiness` is the canonical Phase 1 launch check. It includes the fixed `phase1` staged-readiness check and staged public-data-quality check. The older `npm run p0:readiness` command remains diagnostic only and cannot override the per-company publication model or the at-least-45 launch threshold.

## 信息架构

### 首页搜索页

首页承担唯一主任务：按城市发现医药公司职位。

未选择城市时，页面只展示：

- 极简隐私同意弹窗，未同意不能使用职位页。
- 城市选择控件。
- 简短覆盖说明。
- 全站最后一次抓取时间。
- 数据来源说明入口。

选择城市后，页面展示：

- 当前筛选摘要。
- 可折叠筛选入口。
- 公司聚合结果列表。
- 结果为空时的放宽筛选建议。

移动端信息优先级固定为：城市选择、结果摘要、公司聚合列表、可选筛选。职位类别、关键词、公司筛选、排序和“近 7 天新增”筛选默认不在首屏全部展开。

职位类别筛选采用收起式筛选面板和可搜索多选。17 个类别不能在移动端首屏全部铺开。结果为空时只提供 2-3 个放宽动作：清空岗位方向、清空关键词、查看该城市全部公司。

### 公司聚合结果

公司卡片默认按公司中文名拼音 A-Z 排序。可切换为最新发布、岗位数最多。

公司卡片收起态展示：

- 公司官方中文名。
- 匹配岗位数量。
- 可选的近 7 天新增提示。
- 展开入口。

公司卡片展开态直接展示岗位列表，不做二级分组，也不做公司内搜索。岗位过多时，先展示前若干条，再提供“查看更多本公司岗位”。

“查看更多本公司岗位”必须是受控加载：默认小批量返回，服务端设置每次展开和总返回上限，不提供无限深分页、批量枚举、导出路径或稳定公共 API 合同。

公司内岗位默认按发布时间新到旧排序；没有发布时间时，按岗位标题拼音排序。

### 岗位行

岗位行保持极简，只展示：

- 中文辅助岗位标题。
- 官方原始岗位标题作为次级文本。
- 公司名。
- 城市或地点。
- 主职位类别。
- 发布时间或近 7 天新增标记。
- “查看官方职位”或“去官方招聘页”链接。

岗位行不展示薪资、学历、经验、岗位摘要、原始部门、原始来源分类、分类置信度、抓取技术细节或公司类型标签。

### 公司覆盖页

公司覆盖页只用于告诉用户当前覆盖哪些公司。页面展示：

- 公司官方中文名。
- 公司官网链接。
- 可追溯的官方招聘入口（如有）。
- 真实的一期状态：稳定更新、核验中、仅官方入口、捕获时无公开入口或用户授权一期排除。
- 公司名称搜索。

排序按公司中文名拼音 A-Z。不展示公司类型和抓取技术明细；状态只描述用户可理解的可用性，不暗示待核验公司职位已抓全。

### 辅助流程

反馈、推荐公司、隐私政策、服务条款和公司覆盖页都是辅助流程，不能抢主搜索路径。

反馈以上下文反馈为主：从公司或岗位附近进入，自动带上公司和岗位上下文。全局反馈入口可以存在，但不放在主搜索操作区。

推荐公司进入后台审核队列，不自动发布到前台。

## 职位分类设计

P0 前台职位类别为 17 类：

1. 销售
2. 市场
3. 商务
4. 渠道
5. KA
6. 医学事务
7. 临床运营
8. 注册
9. 药物警戒/安全
10. 研发/科学
11. 生产/工程
12. 质量
13. 市场准入/政府事务
14. 数据/IT
15. 供应链/采购
16. 职能
17. 其他

分类是可选增强，不是发布或上线条件。增强可用时可采用 AI 优先，并保留少量高风险硬规则防止明显误分；增强不可用或置信度不足时使用基础类别，不隐藏已通过官方来源验证的职位：

- 医学信息沟通专员、医学信息沟通经理、医学信息沟通大区经理、医药代表、学术代表归销售。
- MSL、Medical Advisor、医学经理归医学事务。
- CRA、CRC、CTA、Clinical Trial、Study Manager、Clinical Project Manager 归临床运营。
- Regulatory Affairs、RA、注册申报、CMC 注册归注册。
- PV、Drug Safety、Patient Safety、药品安全、药物警戒归药物警戒/安全。
- Compliance、Legal、法务、合规归职能。
- Product Manager、Brand Manager、Marketing Manager、产品经理、品牌经理、市场经理、市场推广归市场，除非上下文明显是技术产品或数据产品。

每次分类保存主分类、可选次分类、置信度、分类理由、模型版本、硬规则命中和人工修正字段。低置信度职位前台放入“其他”，后台进入审核队列。

## 翻译与中文展示

前台界面与说明使用中文。公司名优先使用中国官网或中国业务中的官方中文名；职位标题始终保留官方原始语言，辅助翻译不可用时允许直接显示官方标题。

英文岗位标题的中文辅助标题是可选增强。置信度可接受时，中文辅助标题作为主标题，官方英文标题作为次级文本；增强不可用或置信度低时，前台直接显示官方标题，不阻断发布。每行不单独标注“机器翻译”，但隐私政策、服务条款或数据说明需要说明辅助翻译仅供参考，官方来源为准。

辅助翻译运行时，其结果必须缓存并允许后台人工修正；未运行翻译不影响职位发布。

## 数据获取设计

抓取入口必须从官方主页或官方招聘页开始。允许从官方链路进入 Moka、北森/Zhiye、Workday、SuccessFactors、Redsea 等第三方 ATS。非官方招聘站只能作为线索，不能作为主数据源。

抓取方式以确定性适配器为主，AI 不作为主抓取器。AI 仅可用于可选的职位分类、标题翻译、异常识别和辅助清洗，任何增强失败都不得隐藏来源已验证的职位。

P0 适配器类型：

- 静态 HTML 或表格页面。
- 官方 JSON/API。
- Moka。
- 北森/Zhiye。
- Workday。
- SuccessFactors。
- Redsea。
- 浏览器兜底。

每个适配器输出统一岗位记录：

- 公司 ID。
- 官方中文公司名。
- 来源类型。
- 官方入口 URL。
- 官方岗位详情 URL 或列表 URL。
- 来源岗位 ID。
- 官方原始标题。
- 中文辅助标题。
- 城市或地点原文。
- 标准化城市。
- 主职位类别。
- 发布时间。
- 首次发现时间。
- 最近一次发现时间。
- 抓取批次 ID。
- 原始证据快照引用。

## 城市与地点规则

城市是必选条件。职位地点判断优先级：

1. 来源结构化地点或筛选字段。
2. 岗位详情页地点。
3. 岗位标题中的城市。
4. URL、页面上下文或其他辅助文本。

多城市岗位只要包含目标城市，就进入结果。全国、中国等地点进入结果，并标记为全国/中国。地点冲突时保守处理：可以展示但降低优先级，并在后台标记为地点冲突待确认。

## 新增与下线规则

第一次合格抓取只记录基线，不对外发布；同一规则连续第二次合格后才可展示，首次展示不显示新增标签。

基线之后首次出现的岗位进入“近 7 天新增”计算。前台支持“只看近 7 天新增”。

职位下线只基于成功抓取批次判断：

- 连续 2 次成功抓取未出现：前台隐藏，后台标记为疑似下线。
- 连续 3 次成功抓取未出现：后台标记为已下线。
- 抓取失败不增加未出现次数。
- 抓取失败会立即停止公开该公司的职位，但不删除职位记录；恢复公开仍需满足当前公司资格规则。
- 职位重新出现时恢复前台显示，并清除未出现次数。

## 后台设计

P0 需要最小可用后台。后台必须登录，单管理员账号可接受，建议强密码加一次性码或二次验证。

后台功能：

- 公司库管理。
- 官方主页、社招入口、校招入口、官方链路证据维护。
- ATS 类型和适配器类型维护。
- 抓取状态、最近抓取结果和失败原因查看。
- 单公司手动重抓。
- 分类冲突、地点冲突、低置信度分类审核。
- 疑似下线和已下线职位查看。
- 翻译和分类人工修正。
- 用户反馈查看。
- 推荐公司审核。
- 安全和反爬日志查看。

## 搜索与数据库

P0 使用 PostgreSQL 保存公司、来源、职位、抓取批次、分类结果、翻译结果、反馈、推荐公司、访问日志和安全事件。

P0 搜索使用 PostgreSQL 索引和全文能力，不引入 Elasticsearch、Meilisearch 或 Typesense。关键词搜索默认所有关键词都需要命中，命中范围包括中文辅助标题、官方原始标题、公司名、标准化类别和必要的关键词扩展字段。

## 安全与反爬设计

保护策略偏强，但不能破坏正常用户浏览。

前台不开放公共 API，不提供批量导出，不提供稳定的第三方数据接口。内部查询 API 必须分页、限流，并避免暴露深分页和全量枚举能力。

推荐部署保护：

- Cloudflare 或同等级 WAF/CDN/限流层。
- 若 Cloudflare 影响中国大陆访问，再切换或并联阿里云 WAF/CDN 等同级方案。
- 源站只允许可信代理或必要管理入口访问。
- Nginx 或反向代理层做基础限流。
- 应用层按 IP、User-Agent、行为频次和路径做风控。
- 可评估 CrowdSec 作为安全事件处理和封禁辅助。
- 对异常访问启用挑战或验证码，正常搜索不打断。

SEO 在 P0 采用保守策略。首页只允许静态外壳和基础元信息被索引，不加载职位结果和运营分析。公司覆盖页和职位搜索需要隐私同意后访问。城市/类别结果页、深分页、组合筛选页、内部 API、后台、批量路径、原始数据路径必须禁止索引。

## 隐私与合规边界

首次访问弹窗必须窄、短、简单。内容只包含一句授权说明、勾选框、隐私政策链接、服务条款链接和进入按钮。用户不同意则不能使用网站。隐私政策和服务条款在未同意前可访问，但不能加载职位结果。

系统记录两类数据：

- 必要安全数据：IP、User-Agent、请求路径、时间、限流事件、反爬事件、异常访问记录。
- 运营分析数据：搜索城市、职位类别、关键词、公司展开、官方链接点击、排序方式、来源页。

未证实结论：韩国服务器上的个人信息跨境处理是否满足中国个人信息保护法要求，当前没有足够证据判断。上线前需要法律或合规专业人士复核。当前临时止血做法是明确告知、取得同意、限制采集目的、限制访问权限、保留删除和导出能力的设计余地。

隐私政策必须明确数据保留期限、删除或导出联系/处理流程、后台访问权限、采集数据类别、采集目的、反爬与安全日志用途。跨境合规结论仍未证实，不能在产品或文档中写成已合规。

## 部署与运维

P0 部署目标为 Docker Compose，包含：

- Web 应用。
- PostgreSQL。
- 抓取 worker。
- 调度器。
- 反向代理。

稳定运行建议 4 vCPU / 8 GB RAM。当前 2 vCPU / 2 GB 轻量服务器只适合原型验证；如果必须短期使用，需要限制 Playwright 并发为 1、降低浏览器抓取比例、把抓取任务错峰执行。

备份每天执行，保留 7-14 天，并提供一条命令恢复到测试数据库。监控覆盖网站可用性、CPU、内存、磁盘、PostgreSQL、备份、抓取成功率、单公司连续失败、证书到期和异常流量。

告警规则：

- 网站不可用：立即告警。
- 备份失败：立即告警。
- 单公司连续 3 次抓取失败：告警。
- 全局抓取成功率低于 80%：告警。

## 传播与增长

P0 不做复杂增长系统。传播重点是让页面可分享、可信、可被搜索发现：

- 首页和公司覆盖页可被分享。
- P0 只做静态首页外壳的基础 SEO，不开放城市/类别结果页索引。
- 不开放深分页和批量数据。
- 公众号、朋友圈、小红书作为上线后运营实验，不进入 P0 开发主链路。

## 测试策略

实现必须按测试优先推进。主要测试对象：

- 来源适配器契约测试。
- 官方链路证据测试。
- 职位标准化测试。
- 城市匹配测试。
- AI 分类回归样例测试。
- 翻译缓存和回退测试。
- 搜索筛选测试。
- 移动端前台流程测试。
- 移动端可访问性测试：触控面积、筛选面板焦点管理、弹窗/抽屉键盘关闭、展开/收起状态读屏可识别。
- 新增和下线生命周期测试。
- 后台登录和人工修正测试。
- 限流、无公开 API、robots 和挑战触发测试。
- 备份恢复测试。
- 监控告警规则测试。

每个新适配器必须有最小样本和契约测试，证明能返回标准化岗位记录。浏览器抓取只作为兜底，优先使用 HTTP、官方 JSON/API 或稳定 DOM 解析。

## 开发拆分建议

本项目不适合一次性全部完成，建议分成四个可独立验证的开发阶段：

1. 数据底座与公司源管理：数据库、公司表、来源表、官方链路证据、后台基础登录。
2. 抓取与标准化：适配器框架、代表性 ATS 适配器、抓取批次、职位标准化、45 家稳定更新目标跟踪。
3. 搜索前台：隐私同意、城市必选搜索、公司聚合、职位列表、覆盖页、反馈与推荐公司。
4. 安全与上线：限流、WAF 配置建议、robots、监控、备份、部署脚本、上线检查。

阶段 2 必须在达到至少 45 家稳定自动更新后，才算 P0 数据源完成。规则冻结后只运行两轮最新验证；第二轮结束仍不足 45 家时暂停并通知用户，且不得对外开放。

阶段 3 的前台开发必须在 Product Design brief 确认后生成 3 个视觉方向，并由用户选择视觉目标后再实现 UI。没有视觉目标时，不直接开写前端 UI。

## 已知事实与未证实事项

已知事实：

- 多个代表性官方来源已经过浏览器或直读验证，包括阿斯利康、诺华、恒瑞、百济神州、复星医药、正大天晴、石药等。
- Moka、北森/Zhiye、Redsea 等 ATS 可以通过官方链路出现。
- 当前未发现成熟开源项目能直接完整覆盖中国药企官方招聘抓取。
- Crawlee、Playwright、rate limit、WAF/CDN、CrowdSec 等可作为可复用基础能力。

未证实事项：

- 所有候选公司是否都能稳定抓取。
- Cloudflare 在目标用户网络中的实际访问体验是否优于阿里云 WAF/CDN。
- 韩国服务器个人信息处理的完整合规结论。
- 各公司招聘页面的长期反爬强度和页面结构变更频率。

验证路径：

- 按候选池逐家公司从官网链路核验社招入口。
- 为每家公司记录两次成功抓取证据。
- 对 Cloudflare 与国内访问做多地区测速。
- 对隐私政策和服务条款进行法律复核。
- 上线后持续做 7 天抓取稳定性观察；这属于上线后监控，不增加本期“两轮达到 45 家”之外的前置门槛。
