# Job Finder 来源与证据编译问题、修复及边界

本文件记录已核实的问题与解决方案，不授予采集、发布、数据库写入、环境切换或补读权限。它不是部署手册，不修改第三方技能。生产原件、完整 SQL、原回执、候选及进程身份仍留在已授权位置，不属于本文件的 GitHub 备份。

## 1. Servier：共享 JSON 的语义可逆不等于字节可逆

### 问题与对照

共享 JSON 编译器把普通字段与共享字段分别序列化。展开 SQL 对象拼接后，嵌套对象的字段插入顺序可能变化。此前序列化不同的两个子树可能因此变成相同子树，改变后续共享判定、声明数量和变量编号。因此“解码对象语义相等”不能证明用冻结编译器重编译后与原 SQL 全字节相等。

原严格重编译门实际拒绝过该包。修复没有删除门、排序全部键、重签原件、改 SQL 或重置期限。R1 使用本次请求所绑定的原 READ_PUBLICATION_CONTEXT 回执恢复丢失的顺序，继续通过语义核对与完整字节核对两道门。

### 修复合同

1. 用当前 PUBLISH 的 requestHash 选择唯一已固定的原 context 描述；不得用“最新一个 context”、相似目录或同一来源替代精确请求绑定
2. 核对描述的路径和原字节 hash，以及原读请求、响应和 host 结果的精确身份、文件 hash 与相互对应关系；核对 SQL hash、run/batch、source/config、candidate。重复、换包、错源、错路径、缺件均拒绝
3. 原读 SQL 必须等于未修改的来源专用 context 编译器输出；context schema 和共享 JSON 编译器本身也须保持固定字节身份
4. SQL 解码结果与原 context 必须语义相等。根字段按固定 schema 顺序构建，嵌套字段保留原回执的插入顺序；不要将语义比较替换成忽略字段的局部比较
5. 用原 context 顺序及已解码 terminal 交给冻结编译器，重新产生全部原声明并逐字节比较。原批次、来源、候选、delta/B 证明和所有期限仍需分别验证
6. 没有本次请求的原 context 映射时，保留旧严格路径，不能自动补造或迁就不匹配结果

原包的完整重编译比较覆盖 2,599,158 字节、136 行。该数量只描述这次核验规模，不是未来包大小或行数上限。测试包含同语义错顺序、内容变化、空白字节变化、错来源/批次/候选/原读身份、交换路径、缺件与重算 hash 后改内容。R1 的 6 项顺序合成测试和 12 项私有原包反例通过。

### 后续修正：原字节 hash 在解码之前

R2 修正了读取固定文件时的 hash 边界：先对原 Buffer 求 SHA-256，再做 UTF-8 解码或 JSON 解析。不同非法 UTF-8 字节可能都被解码成替换字符；若先解码再 hash，就无法证明原始文件字节身份。BOM、空白、换行、Unicode 表示和属性顺序也不能先归一化后冒充原字节身份。

原字节 hash 通过不等于 JSON、schema、请求绑定或内容正确；后续门仍必须执行。R2 的 6 项原字节合成测试、保留的 6 项顺序测试及 11 项原包只读核验通过。R2 在 R1 成功之后只修未来本地审查链，没有重新采集或重新发布；不能把 R1 生产成功写成 R2 生产验证。

### 直接 Python 调用必须显式设置来源

一次直接 Python 审查调用遗漏 JOBFINDER_CLOUD_SOURCE_ID，子进程导入 native compiler 时选择了默认来源，触发 READ_COMPILER 门。正式 host 调用原来已经正确设置来源。修复是让直接调用显式传入目标 source，并确保两个 Node 子进程在导入模块前继承该值；不改变全局默认来源，不改 compiler 以接受错误来源。记录这次调用错误，不能归因于原包损坏。

文档示意中的 source 只能使用纯合成标识；实际值从已批准的目标合同取得。不要在日志中输出完整环境或秘密。

### 已成功的边界

2026-10-07：R1 对应运行完成提交，原进程 exit 0；随后公众同批验收为 CURRENT，94 个岗位。原始 95 条按既有规则分为 94 个公开岗位与 1 条已有 UNKNOWN，不把 UNKNOWN 说成已解决。95 条物理记录本次零写入，不意味着无数据库操作或全库零写入。旧失败、R1 成功和 R2 后续本地验证分别保留。

## 2. GSK：官方地点回退必须与严格重放一致

### 原问题

原列表及详情的标准 locations 都为空，但官方详情包含两个明确且一致的主要工作地点字段。旧解析路径未识别该官方信息。职位标题、招聘主体、业务区域和“China”本身都不能替代实际工作地点。

修复限定在既有 GSK 官方来源、公司、入口、组织、站点、social/Open profile 内。来源配置、入口、范围、完整分页、证书类型、SQL 与主备 reader 合同均未改变；没有按已知 job ID 或预期数量写特例，没有启用部分发布。

### 严格回退合同

- 仅在列表与详情的标准 locations 都确实为空数组时进入回退。缺字段不等于空数组；已有标准地点沿用原路径
- 先验证官方请求及详情身份，再绑定列表/详情的 ID、组织、标题、open 状态、来源日期和现行 siteId 规则。不能由同名职位或相近时间推定同一条记录
- 按已审阅的字段 ID、名称和值类型读取 Req status、Primary job posting location、Primary location 与两项 Additional 字段。状态必须为 Open；两个主要字段清理空白后必须完全一致，附加地点必须为空
- 整个地点标签必须表示明确内地城市，或该城市加单一办公设施；locationRaw 保留完整地点标签（现行合同先做 NFKC 与空白清理，不等于原响应字节）；原始未清理标签仍留在绑定的详情原件中。城市只做已审阅映射。不按子串猜城市，不把未知当境外，不用标题推断地点
- 境外/港澳台、未知城市、多城市、远程/选择标记、不同主要地点或设施、新增非空未审阅地点字段均失败关闭。某些无法识别但可能有效的地点也应留待审阅，不能自动扩规则
- 抓取端与独立严格重放端采用同一语义合同。重放仍需独立从绑定的原始入口、分页和详情重建地点，再逐项比输出；共享一个纯函数不等于省掉证据核验
- 严格绑定原件集合为实际入口、全部分页与所需详情；缺件、脱敏替代件、重复/额外未绑定原件、篡改输出城市/原标签均拒绝。来源日期没有时区时不擅造 officialPublishedAt；无依据注入日期也拒绝

72 项聚焦测试及 15 项实际 compiler、49 个迁移的进程内 SQL 到双 reader 测试通过。内存数据库不证明真实 Supabase、多会话或 native 扩展。候选与旧基线的相关回归均有相同 13 项失败，全库 typecheck 亦有相同 13 条已有错误；只可说未新增，不能说全库通过。

### 已成功的边界

2026-10-07 的后续新真实批次公开 67 个岗位，仅新增 2 个上海岗位；66 条原物理记录全不变，原 65 个公开岗位的业务内容保持。原失败为零 PUBLISH，保留为旧失败。早先独立补读只能证明补读时的详情，不能冒充原失败批次的脱敏详情原件。

这些统计是该次已核结果，不是解析逻辑的数量目标或未来完整性依据。

## 3. Novo：原执行监控与功能隔离

本轮问题与修复详见[原执行监控、预算与功能隔离](../../skills/job-finder-aliyun-release-recovery/references/monitor-evidence-and-functional-isolation.md)。这里保留项目结果索引，避免把具体运行身份复制到通用技能。

- 旧运行最后应用层错误后，精确源码/运行树及全部已审控制流证明未来没有新的应用层 HTTP/PUBLISH 路径；原 dispatch owner 已结束且无在途 SQL，当前相关锁/事务为空。保持旧 OS UNKNOWN，在唯一 publisher、独立新 batch/run 和原 starter 条件下继续。取消文件没有确认，不写取消成功；此判断不能用于盲重投旧调用或未知 root 命令
- 新运行改用同一串行 loop 在采集期间轮询原 exec，而非等 CHILD_EXIT 后才取证。十五个原回包已保存回读，真实非零退出与各监督层一致。本次单 URL 四十五秒限制导致采集失败，零 PUBLISH、无新成功观测；只证明监督恢复，不是 Novo 成功，也没有证明延迟属于官方站点或平台代理
- 恢复预算固定来自原 WRAPPER_START.outerDeadline 与 timeoutMs，不从较晚 recordedAt 或丢失 store 后的当前时刻重新计时。PUBLISH 前读取同一原预算；该预算不改变数据库自己的期限门
- r3 独立审查又发现 await 后未重核 run/batch/session，以及预算读取失败后残留半成品 lease。原代码的三项 scope 反例、两项 lease 反例先红灯；窄修后 129 项通过，当时独立审查只闭合这两项已报告问题，并在无 active 时安装。这不证明真实 SQL 边界或完整身份已闭合；后续纠正见下节。r3 尚未有真实 PUBLISH 成功验证，旧 UNKNOWN 保持原结论

### 后续独立复核：r3 仍有最终执行边界缺口

2026-10-07 对 Hansoh/Fosun C51 r3 候选的独立 VM 检查复现八项问题。owner 在调用 helper 前检查了 scope，但 helper 随后还等待 envelope 和 dispatch marker；这些等待中 scope 变化或原预算到期，实际 SQL stub 仍被调用。入口的候选、build、来源等验证也没有固定完整原快照并在最终边界重核。terminal poll 的 await 返回后，旧 session 的终态还可能被接受到已变化的当前作用域。已安装 Novo C59 r3 的相关文件哈希与受影响实现相符。

因此，早先“独立审查闭合”只描述当时两项发现。完整调用链的审查与测试覆盖不足已经确认，不能把 129 项通过写成所有异步边界都安全，也不能把后续 C51 修复自动算到 Novo C59。

r4 将同步、必须返回 true 的最终 guard 放在 helper 全部准备 await 之后，紧邻真实 SQL 调用；guard 与调用之间没有 await。原身份使用独立深拷贝快照，覆盖完整 source/project/config/root、build/candidate、review/request/hash/SQL 与 run/batch/session/relay。最终门同时重核原绝对预算和请求期限，并传递到 owner 管辖的非 PUBLISH SQL 路径。terminal raw 先按原身份保存，证据回读与 wrapper 状态读取后的作用域都须重核，接受终态前再次核对。

晚拒绝时可能已有 dispatch marker。保留 marker 与原请求；本次 NOT_INVOKED 不代表回滚、全局零写入或允许重投。原 UNKNOWN、noWriteEstablished=false、retryAuthorized=false 与不重放 PUBLISH 的边界保持。

独立审查对冻结的 Hansoh/Fosun C51 r4 包运行 683 项，全部通过；原八项反例也全部闭合，其中六项没有 SQL 调用，两项保留完整 raw 且没有接受终态。本文核对该审查与证据字节，没有重新执行这 683 项。复用实际 r4 代码的合成回归，不增加另一份简化监控模型。

2026-10-07 22:05 UTC 的准备检查点：Hansoh/Fosun 的 69 个未绑定 r4 源文件已安装并核验字节，两份独立 PREPARED 已生成；activation 尚未安装，也没有真实采集或 PUBLISH 成功验证。该检查点的已安装 Novo C59 仍为受影响的 r3，保持禁止新启动，未由此 r4 包修复。各对象后续状态须按其新回执分别更新；旧 OS UNKNOWN、未确认取消与 r2 零 PUBLISH 的采集失败保持原结论。

## 4. 备份和验证边界

官网入口原件曾含凭据格式值。值未进入本文、合成测试或 GitHub，也不应以替换样式实例来展示。包含该值的原聚合包和入口整件不外传；其余已批准的四个成员按原 hash 恢复。应明确原聚合包/入口未备份，不能称全原件可恢复。无匹配的完整 SQL/解析结果也只有在原有授权范围内才可发送；“未检出”不是扩大数据分享许可。

项目经验文档只备份经检查的文档和纯合成测试。安全源码备份、私有原件备份和实际运行恢复分别验收。旧 Ali UNKNOWN 与未闭环来源保持原结论。本地模型测试不会关闭这些缺口。

运行同目录下 tests/source-evidence-invariants.test.mjs 使用 Node 内置测试器：`node --test docs/job-finder/tests/source-evidence-invariants.test.mjs`。测试只验证简化模式，使用虚构对象、虚构来源和固定本地子进程，不读取生产、不联网、不触发采集或发布。它不替代原应用测试和已存生产回执。
