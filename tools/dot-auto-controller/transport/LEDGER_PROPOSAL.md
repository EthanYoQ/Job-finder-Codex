# Same-Supabase execution ledger: source implementation, not deployed

The selected durable fence is in the existing Supabase project, using the same approved direct PostgreSQL connection. `proposal/jobfinder-control-ledger.sql` now contains concrete DDL and four fixed functions. It is a SOURCE PROPOSAL, not an installed migration and not a fabricated Prisma migration filename. No SQL, role, grant, credential or deployment action was executed.

## Implemented contract

The trusted first compiler result now retains `packet.expectedBatch`, copied from the original `control.planned.batch`. It does not change the native SQL or invent a new holder/deadline. `ledger-contract.mjs` validates serialized wire input and fixed reply identity; its checks do not replace the SQL checks.

- `claim_dispatch_v1(original jsonb)` returns `{state:"MAY_HAVE_BEEN_SENT",original:<unchanged exact JSON>,claimedAt}` only after an INSERT. Acknowledgement is not proof that native publication occurred. No UPSERT and no repeat-claim success branch exist.
- `read_unresolved_v1(project text, source text)` returns `{schemaVersion:1,projectId,sourceId,ledgerVersion:"dispatch-intent-v1",checkedAt,unresolved:[...]}`. The unresolved array is GLOBAL across all sources; the source argument is not a filter.
- `read_dispatch_v1(project text, request uuid, requestSha256 text)` returns `null` for an absent exact identity, otherwise `{state,original,claimedAt,resolvedAt}`. It never creates authority to resend.
- `resolve_committed_v1(project text, request uuid, requestSha256 text)` returns `{state:"COMMITTED_EXACT",requestId,requestSha256,resolvedAt}` only after observing the native exact terminal result. Nonexact/missing/partial outcomes return `{state:"HOLD",requestId,requestSha256,reason:"NATIVE_COMMIT_NOT_EXACT",retryAuthorized:false}` without changing the row. A missing original intent is an error. A repeated resolution reads the retained already-verified terminal fact; it cannot mutate the original intent or mint a ticket.

`original` has exactly 16 keys: schemaVersion, projectId, candidateId, sourceId, sourceConfigSha256, batchId, sourceResultId, requestId, requestSha256, sqlSha256, holderId, dispatchBefore, expiresAt, overallDeadline, expectedSourceResult, expectedBatch. Deadlines are original integer milliseconds. Expected source/batch are JSON serialization of the original native first compilation, with millisecond UTC date strings. SQL text and secrets are not stored.

## Server invariants

- Immutable original intent, request, holder, hash and native tuple. Deletion and replacing/reopening a resolution are rejected by a trigger. The login has no ledger table DML.
- Permanent uniqueness on request UUID, request hash, SQL hash, holder UUID, source-result ID, original candidate/source/batch/result tuple, and batch/source. Changing request/candidate IDs cannot reopen the same native tuple.
- A partial UNIQUE index on the constant `true` for `MAY_HAVE_BEEN_SENT` permits only ONE global unresolved intent. A new source or batch cannot bypass a prior UNKNOWN.
- Preclaim uses a NEW dedicated autocommit connection and must await the complete `pg.query` promise (ReadyForQuery after implicit transaction commit), not a row event. Do not wrap claim in an outer BEGIN or reuse an open transaction. A function result alone cannot prove that an outer transaction committed. Session startup pins and verifies `synchronous_commit=on`; claim and resolution reject any other setting. The fixed controller client enforces the fresh-connection sequencing, which still needs real PostgreSQL tests.
- Preclaim requires original dispatch-before to remain in the future both before and after INSERT. Existing native PENDING/RUNNING or a held formal-crawl row blocks it. These reads do not replace the unchanged native mutex, table locks, context CAS or expiry gates: other historical writers may race; native publication still owns that protection.
- Resolution locks only its own ledger row. A SINGLE native SELECT snapshot verifies all 57 original exact source fields using the native `CrawlBatchSourceResult` composite type, all planned batch immutable fields using `CrawlBatch`, final SUCCESS and all 11 counters, exactly one source in the batch, the CURRENT member count/current hash/aggregate hash, and the released formal-crawl holder. No dynamic SQL or caller-supplied status/callback is evaluated.
- Batch heartbeat changes during native finalize and is therefore checked as a terminal timestamp, not compared with its original planned value. Time bounds retain the native allowance of up to one second of acquisition clock skew and one millisecond for `TIMESTAMP(3)` rounding. Native source timestamps are compared as typed values, not `to_jsonb` formatting strings.
- Only verified COMMITTED resolution releases the global unresolved slot. The old tuple remains permanently non-replayable. This database resolution is not a frontend or child-process success claim; the controller must still verify its existing native exact outcome, actual child termination and current public reader/API gates before calling it.

## Deliberate HOLD boundary

There is NO absence/rollback/clear resolver. Absence before expiry is inconclusive; absence after expiry alone cannot prove that no original in-flight transaction will later commit. No safe bounded synchronization proof for that negative case has been established here. Therefore a crash between claim and native send can leave a false-positive UNKNOWN that remains HOLD. The implementation does not fake-clear it, renew dates, or replay. A future absence resolver needs a separately reviewed synchronization proof and real late-COMMIT tests against the unchanged native locking protocol.

## Security and approval boundary

The proposal creates a private `jobfinder_control` schema, a dedicated `dot_jobfinder_ledger_owner` with NOLOGIN/NOINHERIT and no administrative flags, ledger owner-only RLS including FORCE RLS, and explicit PUBLIC/anon/authenticated/service_role revocations. The owner has only SELECT on the four native evidence/lock tables plus the qualified digest function. It does not acquire native DML or MAINTAIN privileges. All definer functions use a fixed empty search path, qualified relations, UTC, and direct `session_user='dot_jobfinder_writer'`; writes require READ COMMITTED. No JWT/API-key path is supported. The dedicated login receives only USAGE and the four fixed EXECUTEs in this private schema, in addition to the separately proposed native publisher ACL.

The SQL intentionally does not adopt an existing owner/schema. Actual installation requires an authorized provisioning principal able to create and assign this scoped owner, plus fresh catalog checks for inherited PUBLIC grants, owner/login membership, RLS compatibility, Data API exposed-schema configuration and security advisors. Do not add the private schema to Data API exposure. Revokes are defense in depth, not evidence of the project's actual Data API settings. PostgreSQL cannot attest a Supabase project ID; approved connection host/TLS and the fixed project binding remain required.

Any provisioning is an action-time authorization boundary. Register the actual migration through the project's normal workflow after approval. Its new history entry changes the native exact migration-history profile: produce and review a NEW profile/build/candidate, retaining the history guard itself. Do not install outside Prisma to evade that guard. No credential handoff/provider has been configured or promised; no secret belongs in code, intent JSON, backups or logs.

## Verification and honest limitations

Offline tests check wire schema/negative inputs, strict query names, exact source/batch field coverage, immutable/global-slot SQL structure, no dynamic SQL or absence-clearing path, owner/RLS/revoke structure, and the factory's original batch retention. A synthetic original owned-acquisition/archive/admission/native compiler integration also exercises the wire validation. These are NOT PostgreSQL execution tests.

The environment has no `postgres`, `initdb` or `psql`; the permitted direct-host DNS probe failed before TCP/TLS/authentication. No live transactional, syntax, privilege, RLS, trigger, migration or Supabase/Aliyun end-to-end tests were performed. Before activation, execute positive and negative tests on a reviewed disposable PostgreSQL 17 fixture matching the production schema, including concurrent cross-source claims, lost acknowledgements, uniqueness wait crossing dispatch-before, resolver serialization, native late COMMIT, source/batch/holder/member mutation, integer/JSON/null/timestamp cases, rollback of invalid claims, schema exposure, role inheritance and denied native writes by the ledger owner. Then perform separately approved actual-environment qualification. Passing offline checks alone does not make this production-ready.
