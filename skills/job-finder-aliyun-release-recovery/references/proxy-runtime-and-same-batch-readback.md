# 代理运行时与同批验收

用于既有授权范围内的 dot 云恢复诊断及同批公开验收。只抽取可复用的判断依据；真实运行身份、批次、岗位、原始响应和秘密留在获准的证据位置。保持主技能的架构、部署与 UNKNOWN 边界；改变用户指定架构、范围或执行环境前，说明原因、影响及替代方案并取得明确同意。

## 区分直连 DNS、代理和运行时能力

- `getent` 等直连解析失败，只说明该解析路径失败。已配置平台代理的环境仍可能经代理访问官方站点；不要由此认定整个 dot 云网络不可用或擅自迁移采集环境。
- 先核对现有进程的解释器版本以及是否请求原生 fetch 的环境代理能力。保留平台代理与 CA 的既有加载方式，通用诊断只报告能力、状态与稳定错误码；不打印、复制或覆盖代理与 CA 环境值。actualNode 与真实执行路径仅留在获准的运行证据中，代理配置值及凭据不得写入技能。
- 选择同一个已获准的官方 URL，使用同一环境进行有界对照：能沿用现有代理/CA 的 curl 与实际 Node 原生 fetch。curl 成功不证明该 Node 支持代理；Node 24 的探测成功也不授权把指定的 Node 22 运行合同换成 Node 24。仅凭异常名称或一次 DNS 失败不能判定站点整体宕机。
- Node 22.19 的原生 fetch 不支持 `NODE_USE_ENV_PROXY`。Node 22 分支从 22.21.0 加入该支持，见 [Node 官方 22.21.0 发布记录](https://nodejs.org/en/blog/release/v22.21.0)。区别原生 fetch 能力、CLI 参数支持与注入的测试 transport；一个通过 mock 的测试不能证明真实网络已通。

## 固定 runtime 与实际启动链

在运行时修复已获准时，使用经官方来源核验且版本固定的兼容发行版；曾验证的 Node 22.23.3 是一个可恢复基线，不是永久升级目标。将精确版本、平台、架构、官方发行与校验来源、归档 SHA256、binary SHA256 纳入受版本控制的 runtime profile，拒绝漂移的 latest 选择与未知字段。

区分安装来源和执行身份：归档哈希证明所选输入，实际进程的 binary 哈希才证明执行文件。按目标环境现行验证器核对版本、平台、架构、真实执行路径及 inode；Linux 可用 `/proc/self/exe` 绑定执行中的文件，并与解释器路径指向的文件核对。不能用 PATH 查到的另一个 Node、调用方声明的版本/哈希或只修改 profile 来替代真实验证。

运行时或受身份合同约束的源树变更后，按现行算法生成并回读新的候选身份；保留旧身份和原证据，不复用旧 candidate、伪造 actualNode 或改写旧失败结论。runtime profile 验证通过也不等于正式启动门已通过。

恢复清单直接核对启动链声明的四个固定文件及其真实字节/哈希：外部进程采样器、取消/监督器、启动身份检查器，以及 producer HTTP 诊断 wrapper。尤其核对 starter 内引用的 supervisor SHA。只确认 manifest 内部自洽，可能遗漏旧 pin，导致 preflight 通过后仍在正式 launch 前拒绝。离线验证应包含真实四文件匹配的正例，以及每次只改变一个固定文件或其 pin 的反例；确认正式启动前拒绝，且未产生采集、发布或库写入。若文件集合或启动合同已变化，先核对当前源码，不能沿用历史数字猜测。

## 原生代理 warning 与机器输出

固定 Node 运行时可能在 stderr 输出 `UNDICI-EHPA` 的 EnvHttpProxyAgent 实验性 warning。仅在机器 JSON 解析/验收边界精确识别已核实的完整 warning 形式及对应提示行；原始 stderr 与子进程真实退出码仍保留在受控证据中。未知 warning、不同正文、额外 stderr、非零退出及解析错误均不能吞掉。不要全局禁用 warning、重写代理环境或放宽所有 stderr，只为让 JSON 验收通过。

## 同批身份、分页与增量结论

- 先固定该次原生采集、执行终态、数据库读回和公开结果所对应的 candidate、source、sourceResult/batch 与证书时间。公开 CURRENT 仅是快照状态，仍需核对确实属于目标批次。
- API 的 `Job.id` 是数据库 ID，不能直接与证书成员的 `jobKey` 相比。从同批原生证据将 `jobKey`/`dedupeKey` 映射到数据库 ID；验证映射完整、唯一，再比较公开 ID 集合、sourceId、sourceResultId，并按成员的 CURRENT/GRACE 状态逐项核对有效生命周期时间。API lastSeenAt 应匹配该 member.lifecycleLastSeenAt，lastConfirmedObservedAt 应对应该成员的原始观测时间。增量 no-op 保留的持久 Job.lastSeenAt 可能是旧物理时间，不能与最新证书 verifiedAt 强等，也不能对 GRACE 强套最新 CURRENT 时间。映射不全时保留缺口，不靠总数相等放行。
- 先读实际 API 分页合同。此搜索接口的 `limit` 限公司数，并非每公司岗位数；`limit=50` 不能解释为最多 50 个岗位。公司分页按真实终止条件收齐，再检查每公司完整岗位集合、唯一性与汇总。
- 增量无重复更新的结论要对应实际 Job 业务投影及物理写入证据。当前岗位未变可以不重复 UPDATE；旧 OFFLINE 记录的 missingCount 改变仍可能是必要写入。不能将二者合并为“整库零写入”，也不能将业务投影未变推成全官网详情内容完全未变。
- 逐源写明实际完成的采集/执行、数据库和公众闭环。部分来源成功不代表全部来源完成；公开 HTTP 验收不证明浏览器五秒行为。结论沿用主技能的分层边界。

该 token 的第二段是 `expiresAt`，不是签发时间；当前合同有效期为 60 秒，约束关联寿命，不是缓存新鲜度 TTL。不得用 `now - 第二段` 计算 token 年龄，或再向第二段加 60 秒。客户端读取该段仅用于提前结束观察；签名、进程归属和有效性仍由服务器验证，不能据此伪造或续期 token。

- 该合同下一次观察默认使用新取得的 token 与 45 秒总预算，已有未结束的观察仍沿用原 token 和预算。固定原 monotonic deadline；取得 check 后，同轮请求保留同一个 token，将其绝对到期时间换算为剩余观察预算，只能收紧原 deadline。计入完整响应读取耗时，并继续遵守主技能已有的整体验收硬时限。
- 返回 FAILED 且回显同一有效 check，表示该关联刷新遇到后台失败。它可能由既有后台重试恢复；在原 token、原预算及协议允许范围内有界等待即可。FAILED 时仍不能 PASS；随后必须取得同批 CURRENT 并完成身份、集合和原始时间核对才闭环。
- 携带 check 的请求返回 FAILED 却不回显 check，可能是过期、非法或属于其他进程的 token 被拒绝；不能据此宣称服务器又连续刷新失败。token 改变、到期、协议不明或预算耗尽时，结束这一轮为未完成/阻断，保留具体原因。
- 普通无 check 的请求会申请新的关联序列，可能推动全站快照读取。不要用频繁新 token 替代等待既有重试。确有必要且在授权范围内另开后续验收时，将它记录为新一轮证据，不拼接前轮分页、掩盖原失败或重置原轮预算。

新 check 只改变关联观察，不会使真实源时间或 Job 内容变新。保留源时间与岗位内容的独立核对，不能以 token 更新或最终 CURRENT 代替数据证据。
